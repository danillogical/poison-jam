# A2h — discover the oversized RegionSize local's origin

**Class:** discovery   **Contract revision:** `A2h-oom-causal-slice-r1`   **Status:** draft

## Sketch
- Claim: identify what defines guest stack local `[ebp-0x24]` before the failing call at `0x00149E4A` and the first unresolved or contradicted producer; do not fix or claim progress.
- Known: no-trap A2g and trapped A4b2 runs both request `0x23B20430`; the call-site `add [ebp-0x24],0x20` acts on `0x23B20410`. The allocator returns `0xC0000017`, then a guest path calls NULL. The trap did not introduce the oversized request.
- Unknowns: which guest definition makes the pre-add local `0x23B20410`, whether its source includes a particular modelled read, and whether archived evidence alone binds that input. A separate NULL-guard repair is out of scope.
- Experiment: check archived no-trap and trapped identities; decode original XBE from the confirmed local definition backward, using only complete invocation-bound evidence; if values are missing, make one short diagnostic-only trapped strict run, bounded by the ~4.77 s observed horizon.
- Outcomes: `O-APU-INPUT` → investigate a named modelled input; `O-OTHER-INPUT` → investigate a positively identified non-APU producer; `O-SEMANTICS` → virtual-memory fidelity discovery/Advisor; `O-OPEN` → one missing-witness discovery; `O-IDENTITY` → provenance repair. No outcome authorizes suppression, arena widening, or allocation fakery.

## Question and starting evidence

**Exact question:** At the trapped strict invocation requesting `598869040` bytes, which guest instruction and live input defined `[ebp-0x24]=0x23B20410` immediately before the `add [ebp-0x24],0x20` at `0x00149E24`, and does its feasible definition chain terminate in a positively witnessed named modelled read, a different positively witnessed input, or a precise unresolved leaf? This is a **size-origin discovery**, not merely frequency characterisation and not a diagnosis that any returned device value is wrong.

The archived no-trap `logs/runs/20260922-224429-003-a2g-304f0-span/` (A2g) log at lines 16990–17000 directly shows the **same** `598869040` request, heap refusal and NULL ICALL, despite preceding the A4b2 trap work. The archived pair `logs/runs/20260927-160330-655-a4b2-gp-trap-trace/` (R1) and `20260927-160335-562-a4b2-default/` (R0) shares exe SHA-256 `BC8E288D…DC51`; R1's full log at lines 17108–17120 records ordinal 184, `NtAllocateVirtualMemory: base=0x00000000 size=598869040 type=0x801000 prot=0x4`, heap OOM, returned status `0xC0000017`, then invalid ICALL `return=0014982E`. R0 is **not** a successful comparison: it hangs in the pending-word spin. R1's XBE-backed dump has known `CONTENT_MISMATCH`; it cannot provide guest memory values at nominal VAs. Original-XBE disassembly in `docs/reviews/a2h-mechanism.md:72-96` supplies the precise seed: `0x00149E24 add [ebp-0x24],0x20`, then `0x00149E4A call [0x1c3f88]` with `&RegionSize`; hence the pre-add value is `0x23B20410`. The log's import name alone identifies the thunk. The 35-run identical-size census is context, not proof of the producing input or of wrong hardware. The record's inference that this size *must* derive from bad input and that the NULL call is necessarily unchecked **must itself be tested**, not assumed: prior no-trap failure rules out a trap-necessary mechanism, but cannot rule out a trap influence on timing or a shared upstream model defect. Toolkit bridge `kernel_bridge.c:755-769,833-856,890-899` directly reads the guest size word, tries immediate heap backing and returns `STATUS_NO_MEMORY` on failure; this shows the present implementation's response, **not** universal NT virtual-memory fidelity. A demonstrated legitimate 571 MB region request might implicate reservation/commit semantics even though changing the arena merely to make it pass remains forbidden. The older `A2h-r6` packet was **retired** on a different, refuted `0x00700010` premise and confers no authorization here.

**Baseline:** game planning HEAD `39021c66d8e11cebd2480d5ff026372762ab6f04` and clean toolkit `c151d4e32a782e4e5adcecbc68afe61ed5fc7e52` when drafted; execution must re-pin both trees and the archived exe/XBE/profile rather than assume HEAD. ## Limits, stops, and closure

No row proves a guest defect, a hardware modelling defect, a repair, survival past 4.77 s, a strict boot/audio/liveness/device claim, or that the invalid ICALL is independent of the failed allocation. **Defect B / NULL error-handling is explicitly out of scope:** a guest-side NULL guard would change title behaviour, could conceal a still-impossible 571 MB request, and is not the causal-size repair that can actually unblock meaningful trapped observation. The observed sequence `STATUS_NO_MEMORY` → NULL ICALL is not, by itself, a proof that the code lacks every conditional guard; a future separate change would need its own provenance and owner/Advisor fidelity decision. A genuinely legitimate 571 MB request selects `O-SEMANTICS` for a separate virtual-memory fidelity discovery and Advisor ruling; this packet itself authorizes no repair. Never suppress `RECOMP_APU_TRAP`, fake an allocation result, widen the arena to manufacture success, enable synthetic completion, or disable failure handling. Preserve original assets/saves and unrelated edits. `PIO_FREE` remains **deferred** under its recorded reopen conditions; `A4b2-r7`, accepted/closed `A4b2-r8`, and `A4b1-r4` stay closed; `0xFFFFB3` stays `UNRESOLVED`. No toolkit change except packet-promoted observation-only diagnostics. Stop on changed identities, displaced/unmapped evidence, malformed/truncated trace, new causal ambiguity, or a request to interpret a device's hardware truth without admissible sources. Acceptance of this discovery checks artifacts, tested classifier where used, truthful limits, and row selection only; it satisfies **no** strict criterion.
