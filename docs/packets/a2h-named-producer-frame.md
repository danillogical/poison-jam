## Sketch
- Claim/class: discover the *actual* call entry and inherited frame feeding `[ebp+0x10]` at `0x00149800` on the failing invocation; no repair or strict progress claim.
- Known: `sub_001497DC` uses `g_seh_ebp` as `ebp`; `[ebp+0x10]` therefore belongs to an inherited frame. Eight direct calls, two three-push leads; a push count alone cannot identify the writer of this frame word.
- Unknown: which invocation/caller return, frame owner, and exact word supplied the failing value; whether a passed argument actually writes that word.
- Experiment: finite original-XBE call-site/return audit, then a single bounded diagnostic capture only if the archived evidence cannot bind the live frame; correlate entry, actual read, and failing kernel call without treating an ICALL history or raw stack as an unwound frame.
- Rows: identity failure → provenance repair; witnessed frame argument → demand-driven argument-origin discovery; witnessed inherited/other frame word → demand-driven frame-word writer discovery; unbound/contradictory → one missing-witness/tooling discovery. No shape preflight (§5.8).

## Question and evidence classes
**Exact question:** On the *same* failing invocation, which verified direct-call return PC and inherited frame address own the word read at `0x00149800` as `[ebp+0x10]`, what value was actually read, and can a specific caller write to that **exact address** be positively linked to it? The accepted allocation log and producer formula are prior **archived observations**; original-XBE bytes and generated ABI are **static structural evidence**; a new diagnostic guest capture, if needed, is **invocation-bound observation** only. `0x23B20410` is the aligned pre-add value, **not** automatically the exact unaligned input (the possible input interval is `0x23B203F1..0x23B20410`). The two three-push sites (`ret=0x0014A6D6`, `0x0014A858`) are leads, **not** attribution: in a frameless callee `[ebp+0x10]` need not equal its explicit third stack argument. The other six one-push sites cannot explicitly supply that third argument, but may still inherit a readable caller-frame word. The verified `PUSH32` evaluates its operand before decrementing `esp`; this proves `sub_0014A83E`'s pass-through expression, not that this was the failing frame.

## Limits, stops, closure
This packet does **not** establish the source of the caller's value beyond a proved writer, a guest-vs-toolkit defect, trap necessity, that a third pushed arg equals an inherited frame word, a repair, survival past ≈4.77 s, or boot/audio/GPU/device/liveness success. A structurally possible path or a matching numeric value without an invocation-bound write is `O-OPEN`, never `O-FRAME-ARG`/`O-FRAME-OTHER`. Stop on changed toolkit assumptions; any future toolkit advance requires re-establishing P4's identity-sensitive discovery-transfer bridge before P4 inheritance. Stop on displaced memory, stale identities, malformed trace, incomplete hook coverage, unknown calls/returns or unsafe instrumentation. No synthetic completion: do not suppress the APU trap or `0x80`, fake the allocation, widen the arena, bypass the NULL call, or propose a guest error-handling change here. `PIO_FREE` remains DEFERRED; do not reopen `A4b2-r7`, accepted/closed `A4b2-r8`, or `A4b1-r4`; `0xFFFFB3` remains `UNRESOLVED`.
