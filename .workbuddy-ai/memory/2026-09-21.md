## Cause B fixed (`db54746`), and it was not Cause B

The "115 remaining deleted gotos are branches into another function's body" story
was mostly wrong. **Only a minority were genuine cross-body branch targets. 71
were phantom functions** created by `probes_as_prologue` accepting a bare
`mov edi,edi` (`8b ff`) as a prologue. `8b ff` is the MSVC hot-patch pad *and*
the 2 bytes immediately before an MSVC switch table, so the pass was claiming
table data as code.

**The rule that works** (in `probes_as_prologue`, helper
`_mov_edi_edi_is_a_prologue`): require a run of >= 4 consecutive dwords that are
each *the start of a decoded instruction*, beginning at entry `+2`. Measured:
60 of 71 suspect entries fail it; 0 of the 292 genuine `gap_prologue` entries do.
**Two weaker discriminators were tried and discarded because they SATURATED** —
"a run of in-.text dwords at +2" passed 71/71 *and* 292/292 (almost any window in
.text holds a plausible address), and "the 32 bytes contain an undecoded
instruction" was 0 for both groups (capstone decodes almost any 32 bytes of
32-bit x86). A test that never says no is not a test.

## What `0x00700010` actually is

`sub_0017DBBD` is the **MSVC C++ exception unwinder**, not game code. Proof:
`0x0017DBA4` is `cmp dword ptr [eax], 0xe06d7363` — the MSVC
`_EH_EXCEPTION_NUMBER` magic. Family: `sub_0017DBA2` clears `[eax+0x7c]`
(`_catchlevel`), `sub_0017DC6E` decrements it, `sub_0017D1F8` is `__SEH_prolog`,
`sub_0017E3F8` reads `fs:[0x24]`/`fs:[0x28]` (`_getptd`), `sub_0017E600` builds
the catch frame and dispatches `call eax` at `0x17E625` — the catch handler.

Crash-dump guest memory at `0x001EB740` shows `0x19930520` (=`EH_MAGIC_NUMBER1`)
at `0x001EB744` and a valid table pointer at `0x001EB760` — so the EH tables are
laid out correctly and `0x00700010` is a **slot in the EH handler table holding
a small integer where a code address belongs**.

**`JSRF_ALLOW_UNRESOLVED=1` diagnostic run closes the easy answer.** Past the
ICALL: `esp=0x6A0CC48F` (not a stack address — stack is `0x00F7xxxx`) and a wild
read at `0x10000FFFC`. So `0x00700010` is a HARD STOP, not a missing callee, and
implementing "one more address" will not fix it. `esp` being garbage is exactly
what a desynchronised SEH unwind looks like → **audit the `fs:[0]` SEH chain and
`g_seh_ebp` first** when chasing what threw.

## Code-range fact worth keeping

`g_xbox_code_lo/hi` is **`.text` only**: `0x00011000`..`0x0018CB30`
(`xbox_memory_layout.c` builds it from sections flagged XBE `0x04` EXECUTABLE,
and only `.text` has it). Every other section — D3D, DSOUND, .rdata, .data,
DOLBY — is outside the range. `0x00700010` is in NO section, so widening the
range would not have helped; don't widen it to mask this.
