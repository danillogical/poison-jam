## Correction worth keeping

The method gate's inner test is redundant (`method != 0x0100u || subchannel != 0`
is always true on that path) and I called it dead code. It is redundant, but its
effect is **deliberate**: the model's contract is "execute only implemented
methods, reject the whole stream otherwise", and `jsrf_nv2a_registers` pins it for
unmodeled surface methods, unbound subchannels, the budget, the sink and the RAMHT
path. Changing it fails that test. Reverted.

So 11 has **no gate to fix**: the work is to implement methods one at a time, each
widening what the walk accepts.

# Milestone 11: the model consumes the title's whole pushbuffer

## What landed (toolkit `bafffae`, game `4fde502`)

1. **The walk is class-aware.** `nv2a_core.c` knew only `NV097_CLASS`; a subchannel
   bound to the blit or 2D-surface class could never be accepted. All four classes
   are already named in `nv2a_regs.h`.
2. **The implemented-method table is generated from measurement.**
   `scripts/gen-nv2a-method-inventory.py` decodes the pushbuffer and emits both
   `docs/jsrf-nv2a-method-inventory.md` and
   `xboxrecomp/src/nv2a/nv2a_method_table.c` -- 246 methods (235 NV097, 8 blit,
   2 surfaces, 1 memcpy). Generated so doc and code cannot drift, and so
   "implemented" means "observed in a real submission".
3. **The sink stopped ratcheting.** `sink_count` was only ever incremented and
   nothing read or cleared it, so it hit its cap and rejected every later
   submission for the rest of the run. The test harness already models it as
   per-submission (`submit_reset` zeroes it).
4. **The staging limits were sized to real content.** The title's first ring is
   **259 packets / 713 words**; the limits were 256 packets and a 256-entry
   buffer. Now 1024 / 4096.

`jsrf_nv2a_registers` was **extended, not weakened**: the methods it used to
express "unmodeled" (0x208/0x20C/0x210/0x214) are ones the title does submit, so
they are implemented now, and the test uses methods absent from the inventory
(0x03FC/0x04FC/0x0FFC/0x17FC).

**Result:** `submit #1 diag=ok`, `GET = PUT = 0x1B24`. The walk completes and the
ring fully drains, where before GET was frozen at 0x1000 for the whole run.
CTest 11/11.

## The remaining blocker, and exactly where it stops

The spin at `0x001914F0` is now the only thing in the way. `0x00191710` calls
`0x191440(7, 0)`, so `eax = 7 - 7 = 0` and the loop exits when `[notify] >= 7` --
and it only behaves while `[notify] <= [dev+0x30]`. With the sentinel `0xDEADBEEF`
in place the subtraction wraps and the comparison inverts, so the wait is
permanent. The model must publish a small fence value, not a sentinel.

**The notify handle resolves.** A probe shows `param` is a RAMHT handle:
`ramht_hit=1`, object class `0x3D` = `NV_DMA_IN_MEMORY_CLASS`, object
`0402B03D 0000001F 00000043 00000043`. The toolkit already has `nv_dma_load()` /
`nv_dma_map()` to decode it.

**But the address does not match yet.** That object decodes to DMA address `0x40`,
i.e. guest VA `0x80000040` on the contiguous-window mapping, while the word the
title waits on is `0x80000000` -- 0x40 apart, with nothing measured explaining the
offset. Two readings: the wait is on a different (or not-yet-observed) notify
buffer, or `nv_dma_map` masks into VRAM rather than the window so a DMA object does
not denote a window address at all. Not guessed.

**Next step:** log, at the spin site, both the value at `[0x19dce0]+0x34` and the
DMA object registered, so they can be compared directly instead of inferred.

## Scheduling limits found while setting this up

Worth not re-testing:

- `FREQ=HOURLY;INTERVAL=1;BYMINUTE=0,30` is **accepted but silently ignored** -- it
  still schedules one run an hour, not two. Do not trust it.
- `FREQ=MINUTELY;INTERVAL=30` is rejected: only DAILY, HOURLY, WEEKLY, MONTHLY and
  YEARLY are supported. **There is no sub-hourly cadence.**
- `FREQ=DAILY;BYHOUR=0,1,...;BYMINUTE=0,30` is rejected: BYHOUR takes a single
  integer, not a list.

So a true 30-minute rhythm needs **two** hourly automations staggered by creation
time -- the phase is fixed when the record is created, so the second has to be
created about half an hour after the first. The user was told this.

# MILESTONE 11 COMPLETE: the title gets past GPU initialisation

## Root cause: a gate, not a missing feature

`xbox_Nv2aClaimRegisterOwner()` clears `g_nv2a_ack_enabled`, and `main.c` calls it
via `nv2a_hook_install_aperture` when the MMIO hook takes the aperture. The whole
ack-thread body was inside `if (g_nv2a_ack_enabled)`, so claiming the register
owner also stopped `fence_mirrors_tick`, `counter_mirrors_tick`,
`frame_counters_tick` and `framebuffer_probe_tick`. Measured: with a fence mirror
registered, `fence_mirrors_tick` ran ZERO times in a 20s run.

The gate is right for the register mutations (busy-bit table, PUT->GET mirror --
both write MMIO). It is wrong for the mirror ticks: they write GUEST MEMORY.
`fence_mirrors_tick` and `counter_mirrors_tick` moved outside the gate;
`framebuffer_probe_tick` stayed inside (it reads PCRTC_START).

## The mirror had never been registered by any title

`xbox_Nv2aMirrorFence(device_ptr_va, put_off, get_ptr_off)` existed and was never
called. JSRF's registration, measured: `xbox_Nv2aMirrorFence(0x0019DCE0, 0x00,
0x34)`.

Device layout measured from the dump:

| field | value | meaning |
|---|---|---|
| `+0x00` | `0x80001B24` | pushbuffer write position (VA) |
| `+0x04` | `0x80008DFC` | current chunk end |
| `+0x24`/`+0x28` | `0x80001000`/`0x80081000` | ring bounds (512 KB) |
| `+0x30` | `7` | the value the wait wants |
| `+0x34` | `0x80000000` | the notify word |

`0x001910E0` computes free space as `chunk_end - position` using
`GET | 0x80000000`; `0x00191440` waits while it is under 0x8000. Here
`0x80008DFC - 0x80001B24 = 29400`, so it waited for the GPU to publish completion
into `[0x80000000]` -- and nothing wrote guest memory, so the word kept the
title's own 0xDEADBEEF sentinel forever.

## Result

`[0x80000000] = 0x80001000` (was 0xDEADBEEF), the spin at 0x00191440 is gone, and
the run reaches **normal_exit** after ~19s with the guest deliberately calling
`HalReturnToFirmware(routine=2)`. Not a crash, not a deadline, not a spin.

Toolkit `7e308cc`, game `9f00de4`. CTest 11/11.
