# Milestone 11: the model consumes the title's whole pushbuffer

## What landed (toolkit `bafffae`, game `4fde502`)

1. **The walk is class-aware.** `nv2a_core.c` knew only `NV097_CLASS`; a subchannel
   bound to the blit or 2D-surface class could never be accepted. All four classes
   are already named in `nv2a_regs.h`.
2. **The implemented-method table is generated from measurement.**
   `scripts/gen-nv2a-method-inventory.py` decodes the pushbuffer and emits both
   `docs/jsrf-nv2a-method-inventory.md` and
   `xboxrecomp/src/nv2a/nv2a_method_table.c` -- 246 methods (235 NV097, 8 blit,
   2 surfaces, 1 memcpy). Generated so doc and code cannot drift, and so
   "implemented" means "observed in a real submission".
3. **The sink stopped ratcheting.** `sink_count` was only ever incremented and
   nothing read or cleared it, so it hit its cap and rejected every later
   submission for the rest of the run. The test harness already models it as
   per-submission (`submit_reset` zeroes it).
4. **The staging limits were sized to real content.** The title's first ring is
   **259 packets / 713 words**; the limits were 256 packets and a 256-entry
   buffer. Now 1024 / 4096.

`jsrf_nv2a_registers` was **extended, not weakened**: the methods it used to
express "unmodeled" (0x208/0x20C/0x210/0x214) are ones the title does submit, so
they are implemented now, and the test uses methods absent from the inventory
(0x03FC/0x04FC/0x0FFC/0x17FC).

**Result:** `submit #1 diag=ok`, `GET = PUT = 0x1B24`. The walk completes and the
ring fully drains, where before GET was frozen at 0x1000 for the whole run.
CTest 11/11.

## The remaining blocker, and exactly where it stops

The spin at `0x001914F0` is now the only thing in the way. `0x00191710` calls
`0x191440(7, 0)`, so `eax = 7 - 7 = 0` and the loop exits when `[notify] >= 7` --
and it only behaves while `[notify] <= [dev+0x30]`. With the sentinel `0xDEADBEEF`
in place the subtraction wraps and the comparison inverts, so the wait is
permanent. The model must publish a small fence value, not a sentinel.

**The notify handle resolves.** A probe shows `param` is a RAMHT handle:
`ramht_hit=1`, object class `0x3D` = `NV_DMA_IN_MEMORY_CLASS`, object
`0402B03D 0000001F 00000043 00000043`. The toolkit already has `nv_dma_load()` /
`nv_dma_map()` to decode it.

**But the address does not match yet.** That object decodes to DMA address `0x40`,
i.e. guest VA `0x80000040` on the contiguous-window mapping, while the word the
title waits on is `0x80000000` -- 0x40 apart, with nothing measured explaining the
offset. Two readings: the wait is on a different (or not-yet-observed) notify
buffer, or `nv_dma_map` masks into VRAM rather than the window so a DMA object does
not denote a window address at all. Not guessed.

**Next step:** log, at the spin site, both the value at `[0x19dce0]+0x34` and the
DMA object registered, so they can be compared directly instead of inferred.

Worth not re-testing:

# MILESTONE 11 COMPLETE: the title gets past GPU initialisation

## Root cause: a gate, not a missing feature

`xbox_Nv2aClaimRegisterOwner()` clears `g_nv2a_ack_enabled`, and `main.c` calls it
via `nv2a_hook_install_aperture` when the MMIO hook takes the aperture. The whole
ack-thread body was inside `if (g_nv2a_ack_enabled)`, so claiming the register
owner also stopped `fence_mirrors_tick`, `counter_mirrors_tick`,
`frame_counters_tick` and `framebuffer_probe_tick`. Measured: with a fence mirror
registered, `fence_mirrors_tick` ran ZERO times in a 20s run.

The gate is right for the register mutations (busy-bit table, PUT->GET mirror --
both write MMIO). It is wrong for the mirror ticks: they write GUEST MEMORY.
`fence_mirrors_tick` and `counter_mirrors_tick` moved outside the gate;
`framebuffer_probe_tick` stayed inside (it reads PCRTC_START).

## The mirror had never been registered by any title

`xbox_Nv2aMirrorFence(device_ptr_va, put_off, get_ptr_off)` existed and was never
called. JSRF's registration, measured: `xbox_Nv2aMirrorFence(0x0019DCE0, 0x00,
0x34)`.

Device layout measured from the dump:

| field | value | meaning |
|---|---|---|
| `+0x00` | `0x80001B24` | pushbuffer write position (VA) |
| `+0x04` | `0x80008DFC` | current chunk end |
| `+0x24`/`+0x28` | `0x80001000`/`0x80081000` | ring bounds (512 KB) |
| `+0x30` | `7` | the value the wait wants |
| `+0x34` | `0x80000000` | the notify word |

`0x001910E0` computes free space as `chunk_end - position` using
`GET | 0x80000000`; `0x00191440` waits while it is under 0x8000. Here
`0x80008DFC - 0x80001B24 = 29400`, so it waited for the GPU to publish completion
into `[0x80000000]` -- and nothing wrote guest memory, so the word kept the
title's own 0xDEADBEEF sentinel forever.

## Result

the run reaches **normal_exit** after ~19s with the guest deliberately calling
`HalReturnToFirmware(routine=2)`. Not a crash, not a deadline, not a spin.

# The advisor is under-used, and the acceptance gate does not fix that

The user's impression was right, and measuring it was worth doing.

**Measured:** five advisor prompts ever, two of which were persistence tests — so
**three substantive consults in ~18 hours**, one in the twelve hours to 15:12.
Counted from the advisor's transcript (`agent-d3294b58`), not the logs: the log
phrase `Using subagent model: kimi-k3` appears 47 times because it repeats across
several lines per turn. **The transcript's user turns are the reliable count.**

**Against the triggers, the 12-hour window met:**
- "two measurements contradict each other" — the skill's highest-value case —
  **four times**;
- "a negative result that would change the plan" — **twice**;
- "the same class of mistake twice" — **once**;
- "genuinely stuck after several attempts" — never.

All four contradiction cases were measurement artifacts found locally, each after
costing a run or a false alarm: the `RECOMP_AC97_READY` "regression" that was an
environment difference; the kernel-log budget that made a live run look frozen;
`named_frames` sampled at the deadline being read as before/after; and symbol+offset
being a mislabel past a body's end. The repeat was the detector "covered vs
reviewed" mistake in two consecutive sessions.

**Why the new acceptance gate would not have caught them:** it fires when a
packet's acceptance is evaluated, and every incident happened *during*
investigation, before acceptance was reached. Necessary, not sufficient.

**Fixed:** the automation prompt now carries all five triggers explicitly, with the
project's own recent examples, and says to escalate on a repeat. The plan's
acceptance rule records that the triggers apply during a packet as well as at its
acceptance. Both say: resume `agent-d3294b58`, never re-spawn.

The asymmetry that matters: a consult costs one round-trip, while a measurement
artifact that is trusted costs a run, an investigation and sometimes a wrong
packet — and the advisor's highest-value contribution in this project has always
been attacking the *measurement method*, not the conclusion.

## A2: the GPU interrupt line (automation run, ~16:00-16:35 PDT)

- Root cause of the three-thread KEVENT block at guest 0x0019D630: the NV2A had
  **no interrupt source**. `kernel_vblank_tick` asserted vblank with

  `RECOMP_VBLANK` removed from the toolkit and from docs/jsrf-run-profiles.md.

  Run `logs/runs/20260922-160535-643-a2-irq-line/`.

## A2b + A2c (evening session)

- A2b: the ABI failure at `0x00048190` was a span cut short at `0x00048305`,
  which is a disassembler `tail_jump_alias` **phantom** (`_build_alias_entries`),
  not a function start. Real body ends `pop edi/esi/ebp/ebx; add esp,8; ret 0xc`
  at `0x0004838C`; the over-long span had also swallowed the shared epilogue at
  `0x00048371` that was trapped as an aborting stub. Game `caef022`.
- **Rule found the hard way: `stack_args` is the `ret N` operand**, not an
  argument count. `0x0004A6C0` is declared 4 and ends `ret 4`. A wrong value is
  invisible in the span and shows up only as an `esp` delta 4 high.
- Two neighbours corrected the same way (`0x00048390`, `0x00048570`).
  `0x00025310` did not recur -> it was collateral from the corrupted frame.
- A2c: a **different** trigger for the same failure mode. A function reached only
  through a data table occurs in no call/jump, so `tools/disasm` never registers
  it and the previous entry's span runs over it. `scripts/check-table-targets.py`
  already enumerates 134 such candidates. Recovered `0x00173DB0` and
  `0x00175300`; game `50cc6a8`.
- New stop, a new class: `[APU] MMIO decode fail ... C5 FE 6F 02` (a VEX/AVX
  instruction) then an access violation reading `0xFE840200`. A host routine
  faulted on the APU aperture and the VEH decoder only handles legacy encodings.
- Traps: capstone in a throwaway script desyncs on bytes that
  `scripts/inspect-jsrf.py disasm` decodes cleanly -- the repo tool is the
  authority for evidence. `report-deepseek.md`'s CURRENT STATE block was rewritten
  in place; A2b/A2c/A2d added to the plan.

## A2d.1 (evening run): a `rep movs` over a device window was lowered to a host memcpy

- Root-caused the APU decode failure: the faulting RIP was in a CRT DLL because
  the lifter lowers guest `rep movsd` to a host `memcpy` when the ranges cannot
  overlap, and the VEH can only emulate the faulting *guest* instruction. Guest
  0x001A1B41, src 0xFE830200 (APU GP window), dst a RAM buffer, 280 bytes.
  Every register in the fault dump reconciled against the 4-argument call site.

  APU model names a read of an unimplemented block instead of returning 0 in
  silence. Game `5e756a7`, CURRENT STATE rewrite `a82f679`.
- Measured: decode failure gone, named frames 109 -> 147, threads 11 -> 17,
